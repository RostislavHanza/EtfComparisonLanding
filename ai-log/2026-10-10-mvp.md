# Funkční MVP — 10. října 2026

## Skutečný schvalovací prompt

```text
Schvaluji implementační plán s následujícími úpravami.
**1. Katalog ETF**
Neomezuj aplikaci pouze na SPY, VOO a IVV.
Připrav rozšiřitelný katalog ETF s vyhledáváním podle tickeru a názvu.
Cílem je mít pro MVP přibližně 15–20 skutečných ETF obchodovaných na NYSE Arca a možnost porovnat až 5 fondů současně.
Pokud nelze některá data spolehlivě ověřit, fond zatím nezveřejňuj. Nevytvářej smyšlené produkční údaje.
**2. E-mailový proces**
Pro MVP upřednostni jednoduché, bezpečné a skutečně funkční řešení.
Uživatel sestaví srovnání, zadá e-mail, dostane unikátní odkaz a po potvrzení přístupu otevře uložené srovnání.
Zachovej bezpečné tokeny, serverovou validaci, základní ochranu proti zneužití a oddělený marketingový souhlas.
Pokročilé funkce, které nejsou nutné pro funkční MVP, můžeš odložit a zdokumentovat.
**3. Data ETF**
Souhlasím s ručně ověřenými daty a týdenní kontrolou.
Připrav seznam schválených zdrojů, postup validovaného importu a evidenci data posledního ověření.
Automatický import zatím neimplementuj, ale navrhni, jak ho později bezpečně doplnit.
**4. Backend**
Použij Supabase, Vercel Functions a Resend podle návrhu.
Připrav migrace, API, integraci s frontendem a potřebné testy.
Pokud nemáš přístup ke skutečným službám nebo chybí environment variables, dokonči vše, co lze připravit bez nich, a přesně vypiš, co musím nastavit ručně.
**5. Priorita**
Nejdůležitější je dokončit funkční cestu od výběru ETF až po otevření srovnání z e-mailu.
Design zatím zásadně neměň. Zachovej současný redakční vzhled.
Po dokončení jednotlivých částí průběžně ověřuj build a testy.
Pracuj na větvi `design-exploration`, aktualizuj dokumentaci a `ai-log/`.
Vytvářej smysluplné commity a pushuj na tuto větev, abych mohl průběžně kontrolovat Vercel preview. Nic nemerguj do `main`.
Můžeš začít s implementací.
```

## Stav a rozhodnutí

- Před úpravou čistý checkout na design-exploration. Přečteny AGENTS.md a předchozí implementace. Lokální autor je RostislavHanza s GitHub noreply; globální konfigurace neměněna.
- Metadata cloudového nastavení neobsahují secret/runtime bindings. V procesu nejsou SUPABASE_URL, SUPABASE_SECRET_KEY/SERVICE_ROLE_KEY, RESEND_API_KEY, RESEND_WEBHOOK_SECRET, EMAIL_FROM, APP_BASE_URL ani RATE_LIMIT_SECRET. Hodnoty nebyly vypisovány. Živé služby zde nelze ověřit.
- Produkční data se nevymýšlejí. Kandidátní seznam je pouze postup pro lidské ověření, nikoli seed. Schválené domény a ruční import zdokumentovány; automatické získávání dat odloženo. Předchozí primární zdroje byly blokované HTTP 403; žádné údaje z nich nejsou nově označené jako ověřené.
- Schválené změny rozsahu (2–5 ETF, skutečné porovnání před e-mailem) mají přednost před původními omezeními prototypu. Produkční data budou z databáze, přístup k uloženému srovnání ze session; ostatní designové návrhy zůstávají explicitně demo.

## Část 1: schema a server

- Připraveny tabulky ETF, kontaktů, consent records, srovnání/snapshotů, tokenů/session, e-mailových stavů, webhook receipts, funnel events a atomických rate limitů. Anonymní/authenticated role mají zakázané tabulky i privilegované RPC.
- API na Vercel Functions, Supabase přes serverový SDK, Resend s unikátním odkazem v fragmentu, jednorázové potvrzení a 30denní HttpOnly session. Tokeny jen hashované v DB; link bez e-mailu. Podepsaný webhook odlišuje doručení od odeslání a potvrzení.
- Připraven validovaný dry-run/import s kontrolou schválených zdrojů, všech polí, data ověření a evidence podmínek použití. Doklad člověka nelze nahradit syntaktickou validací.
- V testech použit PostgreSQL engine PGlite: skutečné migrace/SQL funkce, ne náhrada databáze prostým mockem. Resend ani živý Supabase nejsou tímto ověřené.
- První kontrola: 5 testů prošlo (2 kalkulačka, 3 databázové scénáře: role/RPC, transakce/token/session/expiry/uložení, rate limit/webhook pořadí a duplicity). Typecheck a build prošly.
- Nastavení, chybějící služby, DNS, testovací příjemci, retence a odložené funkce jsou v docs/SETUP.md. Produkční spuštění nesmí být označeno za dokončené bez ověřeného katalogu a testovacího e-mailu.

## Část 2: frontend, provoz a ověření

- Výchozí Editorial je napojený na API, nikoli na demo data. Katalog s hledáním tickeru/názvu a 2–5 fondy, tabulka primárních zdrojů a dat, kalkulačka/graf, skutečný POST žádosti, explicitní potvrzení odkazu, GET uloženého snapshotu a PUT úprav. Prázdný/nedostupný katalog nemá demo fallback.
- Předchozí prototyp zachován výslovně přes `?variant=editorial-demo`; dalších šest palet i starší varianty zůstávají demo. Původní typografie/paleta zachované.
- Přidáno nastavení skutečného správce; bez OPERATOR_NAME/OPERATOR_CONTACT nelze uložit kontakty. Marketing není povinný a je oddělený. Volitelné měření je opt-in; odvolání odstraní přiřazené události/atribuci na serveru bez smazání vyžádaného srovnání. Chybu odvolání UI přizná a umožní opakovat.
- Druhá migrace přidává úklid 30denních nepotvrzených a 90denních potvrzených srovnání, závislých/osamocených kontaktů, session, limiteru a 90denní analytiky. Denní chráněný Cron je pouze retence, ne automatický import ETF; preview vyžaduje vlastní úklid.
- Lokální adapter používá skutečné Vercel handlery a Vite proxy. Zkontrolován HTTP požadavek přes spuštěný dev server: katalog 503 bez konfigurace; nepovolený Origin 403; nepovolená metoda access 405. Žádné skutečné kontakty/e-maily při tom nevytvořeny.
- Kontrola Resend SDK odhalila nutný API klíč při konstrukci verifieru. Opraveno; test podpisu ověřuje platný/tampered/starý payload. Raw webhook se skládá z bufferů, aby podpis nerozbilo dělení českého UTF-8 znaku mezi chunky.
- Browser test původně selhal při otevření fragmentu v již načtené záložce. Přidána navigace hashchange/popstate; první oprava ještě neřešila odstranění fragmentu mezi událostmi. Definitivní oprava čte původní HashChangeEvent.newURL. Celý test po opravě prošel.
- Prošly `npm ci`, build a samostatný typecheck. Finální `npm test`: 15 testů, 15 passed, 0 failed/skipped (aplikace/mail chyby/hash/limity, validace/import/HTTP, skutečné SQL migrace/session/expiry/RLS/webhook pořadí/retence/odvolání analytiky, raw podpis).
- Prošel `BROWSER_PATH=/usr/bin/chromium npm run test:browser`: izolovaných 20 TEST ONLY fixtures, hledání, pět fondů, reaktivní výpočet, formulář až po konfiguraci, marketing false, návratový odkaz, obnovení/PUT/reload, opt-in/odvolání, všechny archivní URL, prázdný katalog/chybějící správce/API outage bez demo fallback. Šířky 320, 390, 768, 1100, 1440 px bez horizontálního přetékání a JS chyb. Browser API je testovací mock; nejde o ověření skutečného doručení.
- `git diff --check` a kontrola běžných secret patternů prošly; sledovaný env soubor je pouze `.env.example`. Nejde o formální bezpečnostní audit.
- Aktualizovány README, PLAN a AGENTS podle schváleného rozsahu, včetně zachovaných dvou reklam, konverzních předpokladů a tří A/B hypotéz. Právní a performance/WCAG audit neproveden.
- Skill cloud-environment-onboarding:setup použit pro opakovatelné prostředí: uložen draft s ověřenými install/start instrukcemi, názvy chybějících proměnných a doménami primárních zdrojů/Resend/Supabase. Tool potvrdil saved a requires_publish; tento krok NEaplikoval konfiguraci ani síť a není důkazem nového přístupu ke službám.

## Zbývající externí blokery

Živé Supabase/Resend přístupy stále nejsou přítomné. Nebyly aplikovány migrace na skutečném projektu, není ověřený produkční katalog 15–20 ETF, nebyla nezávisle prověřena dostupnost oficiálních API/licence zdrojů, neodeslán skutečný testovací e-mail, neověřeno Vercel nasazení ani živý webhook. Ruční kroky a akceptační průchod jsou v docs/SETUP.md; data v docs/DATA_SOURCES.md. V repozitáři nejsou smyšlené produkční údaje. Tyto blokery brání označit web za připravený k produkční kampani.
